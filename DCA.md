# DCA in 895 public strategies

Someone asked, in the freqtrade Discord, whether anyone would share results
from a DCA strategy. This corpus already had the answer sitting in it, so
here it is.

DCA — averaging into a position — is not an opinion in freqtrade. It is two
things in the code: `position_adjustment_enable`, and a method called
`adjust_trade_position` that returns a stake. Both have to be there. So the
question "how does DCA do" becomes a question you can run.

Every number below is produced by [`dca.py`](dca.py) from
[`LEDGER.csv`](LEDGER.csv), the result cards, and
[`dca_ab_2024.json`](dca_ab_2024.json). None of them are typed by hand.

## How the detection works, and why not grep

Searching for the word `position_adjustment_enable` counts a comment, a
docstring, and commented-out code as the real thing. It also merges two
different classes that happen to share a file: flag on one, method on the
other, and the file looks like it has DCA when neither class does.

So `dca.py` parses the AST, finds the `ClassDef` whose name matches the
strategy in the ledger, walks base classes defined in the same file, and
requires all three of: the flag, the method, and a method that returns a
value rather than falling through to `None`.

## Nine strategies were measured without the DCA their author wrote

This is a correction to this repository, not a finding about anyone else.

`adjust_trade_position` is only called when `position_adjustment_enable` is
set. freqtrade resolves that attribute in this order — configuration first,
then the strategy class, then the default (`strategy_resolver.py`). This
sweep supplies its own `config.json`, which does not mention the flag, so the
strategy attribute wins. That is what makes the other 82 measurable.

But nine strategies define the method and never set the attribute in the
class. Their flag lives in the `config.json` shipped with their repository —
which this sweep replaced with its own. **Their DCA did not run here.**
`NostalgiaForInfinity772martinsk3` is one of them.

Their numbers in the ledger are not wrong. They are about a different thing
than their author built. The column `suppressed_by_our_config` in
[`DCA.csv`](DCA.csv) marks all nine.

There is a general warning in this for anyone copying a `.py` file out of a
repository: **a strategy's behaviour is not all in the strategy file.**
Take the file without the matching config and you get, silently, a different
strategy.

## What the mechanism does to the shape of the result

Win rate goes up by about fifteen points. The average loss goes from under
twice the average win to about five times it. Expectancy per trade does not
move, and zero strategies clear the ladder in either group — same as the
corpus as a whole.

That is the whole trade, in numbers, from real code rather than argument:
DCA moves probability mass out of frequent small losses and into rare large
ones. Nothing is created.

Six DCA strategies beat buy-and-hold out of sample, against 2.7% of the
non-DCA group. Each of the six was inspected: one returns +29,748,386% and is
flagged by recursive analysis, three are portfolio rebalancers that never
reached the trade-count gate and were never successfully look-ahead tested,
two more are flagged for recursion. **None of the six survives inspection.**

## The measurement that actually decides it

Comparing DCA strategies against non-DCA strategies compares *authors*, not
mechanisms — different timeframes, different indicators, different skill.

The experiment is available because configuration beats the strategy
attribute: putting `"position_adjustment_enable": false` in the config turns
the mechanism off in *the same strategy*, on the same candles, with the same
fee. Verified on the subject rather than assumed — with the flag off, the
number of entry orders per trade drops from `{1: 171, 2: 29}` to `{1: 208}`.

Twenty-nine pairs ran. In thirteen of them the mechanism never placed an
order in 2024, so those pairs carry no information about it and are set
aside. Sixteen remain.

**And then the denominator decides the answer.**

A ladder strategy reserves capital. Its `custom_stake_amount` divides the
first entry by the ladder multiplier when the flag is on — literally, in
`AlexBattleTankKillerV40H`:

```python
if self.position_adjustment_enable:
    calculated_max_dca_multiplier = 1 + Σ volume_scale**k
stake_amount = proposed_stake / calculated_max_dca_multiplier
```

With the flag on, that strategy stakes 28.38 where it stakes 49.47 with the
flag off — a ratio of 1.743. Its result changes from −1.26% to −0.70%, a
ratio of 0.557. The difference is explained by size, entirely, and the
mechanism placed no orders at all that year: 635 trades, 635 entries, 635
exits, both runs.

So "the wallet lost less with DCA on" is true and uninformative. It lost less
because it was smaller. Divide by the capital actually deployed and the sign
flips: better in 3 of 16 instead of 15 of 16.

## What this does not say

It does not say DCA is bad in general. It says what happened to sixteen
community strategies on eight pairs in one year, measured both ways.

It does not test averaging schedules that nobody in this corpus wrote —
geometric, Fibonacci, volatility-scaled. Those are absent here, not refuted.

The 2024 window is a rising year. A bear-market replication is the obvious
next thing and it has not been run yet; when it is, it goes in this file
whichever way it comes out.

## Reproduce it

```
python corpus.py --fetch          # the strategies
python harness.py                 # the result cards
python dca.py --publish           # DCA.csv and the block above
```

The paired A/B itself takes two backtests per strategy — one with the flag
on, one with it forced off in the config — over `20240101-20250101`, and is
what produced `dca_ab_2024.json`.
